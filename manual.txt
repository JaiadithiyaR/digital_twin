--------------------------------------------------------------------------------
 0. WHAT THIS SYSTEM IS
--------------------------------------------------------------------------------

A modular AI-driven self-adaptive Digital Twin (DT) of a real 5G RAN. It:
  - Ingests real, exported OAI RAN KPI telemetry, replayed in genuine
    timestamp order (or an OAI-schema-shaped mock generator for unit tests).
  - Keeps a continuously synchronized DT state (D1).
  - Runs 7 dependency-aware prediction models for real RAN KPIs: downlink/
    uplink BLER, downlink/uplink PRBs used, downlink/uplink throughput, and
    downlink RLC delay.
  - Computes a deterministic per-component and system-wide fidelity score
    (the ORIGINAL RMSE/MAE/Wasserstein/MK-MMD formula, unchanged by the
    component-set migration).
  - Detects two kinds of adaptation triggers (external drift events, and an
    internal fidelity-degradation trigger) and reacts using a Google
    Gemini-backed Decision & Root-Cause Analysis Agent.
  - Executes one of three adaptation strategies (recalibrate / regenerate /
    expand_scope) inside an isolated sandbox, deterministically verifies the
    result, and only then promotes it to production (with rollback safety).
  - Records every adaptation event in an auditable lifecycle log (including
    which telemetry source/run ids/replay speed were in effect) and
    generates a human-readable maintenance report.
  - Runs continuously and autonomously (no human in the loop).

19 modules + 2 extra components (D1 state store, D2 RAG knowledge base) + 6
agents. Full detail in CLAUDE.md. OAI-specific design (real KPI catalog, the
causality-correct lagged-feature replay design, the 7-component dependency
graph) is in docs/oai_twin.md.

 1. PREREQUISITES
--------------------------------------------------------------------------------

  - Linux (this was built/tested on WSL2 / Ubuntu-family).
  - Python 3.10+ (this machine uses 3.14.4).
  - git.
  - Read access to a real exported OAI RAN KPI dataset (CSV export under a
    directory matching config.data.oai_root — default
    /home/harie06/oai_db/data/rankpi_kpi/ — read-only, never copied into
    this repo). Only needed to (re)build data/processed/oai/ (section 3b);
    the pytest suite and mock-telemetry runs do not need it.
  - (Optional but recommended) a real Google AI Studio API key, so the LLM
    agents genuinely run instead of falling back to their deterministic
    default. Get one free at https://aistudio.google.com/apikey
  - No GPU is required anywhere in this system. No C++ toolchain is required
    anymore (the NS-3 build step is retired — see archive/ns3_sim/README.md).

--------------------------------------------------------------------------------
 2. ONE-TIME SETUP
--------------------------------------------------------------------------------

  cd dt_adaptation

  # Create and activate a virtual environment
  python3 -m venv .venv
  source .venv/bin/activate

  # Install all Python dependencies (idempotent, safe to re-run)
  pip install -r requirements.txt

  # Create your local secrets file (never committed to git)
  cp .env.example .env

  # Edit .env and set a real key:
  #   GOOGLE_API_KEY=your-real-key-here
  # (GEMINI_API_KEY is also accepted; GOOGLE_API_KEY wins if both are set.)
  # Without a real key the system still runs correctly: every LLM call
  # degrades gracefully to a deterministic fallback and logs a WARNING every
  # time it does so — it never fakes an LLM response.

  # Verify the environment is genuinely ready (directories, .env, deps,
  # config all load) — this is non-destructive, safe to run any time
  python scripts/setup.py

  # Expected final line: "[setup] OK — environment ready"

All tunable parameters live in config/settings.yaml. You should not need to
edit it for a normal run, except config.data.oai_root if your real OAI export
lives at a different path than the checked-in default.

  .venv/bin/python -m pytest tests -q

Notes:
  - No test hits a real network/API by default. The Google AI client's
    transport is mocked in every test except ONE: a live-smoke test in

--------------------------------------------------------------------------------
 3b. BUILD THE REAL OAI DATASET (one-time, before first bootstrap/replay)
--------------------------------------------------------------------------------

Reads the real, read-only OAI export and writes the model-ready,
config-driven train/val/test splits (config.data.splits — run ids, never
hardcoded in code) this system actually trains and replays from. Never
copies the raw CSVs into this repo.

  python scripts/build_oai_dataset.py

Produces data/processed/oai/{train,val,test}.parquet, feature_schema.json,
and data_report.md (NaN/reset/gap counts per split, and an honest note on any
excluded incomplete run — e.g. this project's own run 10 was excluded for
exactly this reason; see docs/oai_twin.md section 1). Run this once before
the first real bootstrap/replay — --mode demo/live and every script in
sections 6-8 read these files.

--------------------------------------------------------------------------------
 4. (OPTIONAL) BUILD THE RAG KNOWLEDGE BASE
--------------------------------------------------------------------------------

The Decision & Root-Cause Analysis Agent and several other LLM-backed agents
consult a read-only RAG knowledge base (ChromaDB, local, persisted to
rag_data/chroma/). Build/refresh it (idempotent — safe to re-run any time):

  python scripts/ingest_rag.py

If you skip this step, the system still runs correctly: every RAG lookup
degrades to an honest "not available" context (logged, never fabricated).

--------------------------------------------------------------------------------
 5. RUN THE FULL SYSTEM
--------------------------------------------------------------------------------

The real continuous loop lives in src/main.py (ContinuousOrchestrator). It
runs: telemetry -> preprocessing -> continuous D1 synchronization ->
dependency-aware DT prediction (the 7 OAI KPI components) -> fidelity
evaluation -> drift/fidelity trigger -> Decision & Root-Cause Analysis Agent
-> recalibrate / regenerate / expand_scope -> sandboxed candidate ->
deterministic verification -> hot-swap promotion or rejection -> lifecycle
record -> repeat, forever, without stopping (Ctrl-C to stop).

  # OAI-schema-shaped mock telemetry (SOURCE=MOCK), runs forever — no real
  # OAI export needed, fast iteration / unit-test-style use
  python -m src.main --mode demo

  # REAL OAI RAN KPI replay (SOURCE=OAI_RAN_REPLAY), streamed from
  # data/processed/oai/ (section 3b) in genuine timestamp order at
  # config.telemetry.replay.speed
  python -m src.main --mode live

  # Bounded run for testing/demo purposes — stop after exactly one full
  # adaptation cycle instead of running forever
  python -m src.main --mode demo --max-drift-events 1

It writes to this repo's real configured storage paths (see section 9) and
logs structured JSON to logs/digital_twin.log as well as stdout.

--------------------------------------------------------------------------------
 6. RUN THE PERMANENT, REPO-TRACKED FULL END-TO-END DEMO/VALIDATION SCRIPTS

Each is an unattended, single-adaptation-cycle run. Each prints its own real
observed results (LLM/RAG availability, live telemetry accumulation, real

no fabricated "success" message anywhere in this system.

  # Mock telemetry — fast (~1-2 minutes), good for quick iteration, no real
  # OAI export needed
  python scripts/run_orchestrator_demo.py

  # REAL OAI run-8 (TEST split) replay at speed=0, with a forced adaptation
  # trigger for determinism (prompt2.md Step 7's required smoke test) — runs
  # real predictions -> real fidelity -> forced trigger -> real decision ->

  # Writes to its OWN dedicated storage path (data/e2e_oai_smoke/), never the
  # shared --mode demo/live paths.
  python scripts/run_oai_e2e_smoke.py

  # All four baseline experiment modes (static / periodic_retrain /
  # rule_based / full) over the same real OAI TEST-split replay, for
  # comparing the real LLM-driven decision agent against simple
  # deterministic baselines
  python scripts/run_baselines.py --mode full

(A REJECT outcome from the verification gate is just as valid and complete a
demonstration as an ACCEPT would be — it proves the deterministic safety gate
is genuinely protecting production, not rubber-stamping every candidate.)

Note on the Google AI free tier: the free tier is capped at 20
requests/day/model. Running several demo scripts back-to-back (each makes
several real LLM calls: decision, verification explanation, maintenance
report) can exhaust that daily quota partway through — when it does, every
subsequent LLM call correctly, automatically falls back to the deterministic
default strategy/explanation and logs a WARNING every time. This is expected,
documented, fail-safe behavior, not a bug: a daily quota exhaustion can never
be waited out by the built-in retry/backoff, so the system correctly gives up
retrying and degrades instead of hanging.

--------------------------------------------------------------------------------
 9. TROUBLESHOOTING
--------------------------------------------------------------------------------

"pip install" fails on a system package
  -> Make sure the venv is active (source .venv/bin/activate) before pip
     install; system Python package conflicts are the usual cause.

scripts/setup.py reports MISSING DEPENDENCIES
  -> Run: pip install -r requirements.txt   (safe to re-run, idempotent)

scripts/build_oai_dataset.py fails with a missing-file / incomplete-run error
  -> Check config.data.oai_root points at your real OAI export, and that
     config.data.splits only names runs with COMPLETE exports (no .partial
     files) -- see docs/oai_twin.md section 1 for how this project's own
     run 10 was excluded for exactly this reason.

pytest gets OOM-killed on "pytest tests -q"
  -> Run tests/unit and tests/integration as two separate invocations
     instead (section 3). This is a known constraint on small/memory-
     constrained machines (this project has observed it directly), not a
     code defect.

test_live_api_smoke_if_key_configured fails with a 429 / quota error
  -> Expected if you already exhausted that day's 20-requests/day free-tier
     quota (e.g. by running the demo scripts in section 6 several times the
     same day). It will pass again once the quota resets (daily, UTC). This
     is a genuine, honest failure by design -- not something to silence.

Decision agent / LLM calls always fall back to the deterministic default
  -> Check .env has a real, non-placeholder GOOGLE_API_KEY (or
     GEMINI_API_KEY) set, and that you have not exhausted the daily free-tier
     quota. The system is still fully functional and safe without a working
     LLM -- every fallback is logged, never silent, and never fakes an LLM
     response -- but you will not see genuine LLM-grounded root-cause
     analysis until a real, working key with quota available is configured.

Want a completely clean slate (fresh D1/model/lifecycle state)?
  -> Everything under data/ (except data/processed/oai/, which is rebuilt
     from the real OAI export, not from live state) and logs/ is gitignored,
     regenerable runtime state. It is safe to delete data/artifacts/,
     data/models/, data/e2e_oai_smoke/, and logs/ and re-run any of the
     commands above -- they will regenerate everything from scratch.
